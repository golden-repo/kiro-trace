# kiro-trace

A small internal web service that collects telemetry (estimated token
counts, real credit usage) and health heartbeats from the Kiro CLI
`telemetry-handler.js` / `telemetry-watcher.js` scripts, stores them in
Redis, and shows them on a live dashboard.

This README assumes little to no prior Python experience -- every step
is spelled out, including what each command actually does.

## The REST APIs

| # | Method | Path            | Called by                        | Purpose |
|---|--------|-----------------|-----------------------------------|---------|
| 1 | POST   | `/api/telemetry` | telemetry-handler.js / telemetry-watcher.js | Push one traceability log entry (same JSON shape already written to the local `telemetry.log` file) |
| 2 | POST   | `/api/health`    | telemetry-handler.js / telemetry-watcher.js | Push a "still alive" heartbeat (session id, machine name, current user, component) |
| 3 | GET    | `/api/telemetry` | the dashboard                     | Read back recent telemetry entries, optionally filtered by session id and/or source-control fields |
| 4 | GET    | `/api/telemetry/analytics` | the dashboard ("Usage Analytics" section) | Read back both **computed totals** (grouped by organization/repository/branch/user/session) and **detailed records** for a filtered, optionally date-ranged selection, plus a daily time series for charting -- see below |
| 5 | GET    | `/api/health`    | the dashboard                     | Read back the latest known liveness status of every handler/watcher this server has heard from |
| 6 | DELETE | `/api/health`    | the dashboard ("Clear heartbeat data" button) | Remove stored heartbeat data for one session (`?session_id=...`) or every session belonging to one user (`?user_name=...`), optionally restricted to one component (`&component=handler` or `&component=watcher`). Exactly one of `session_id`/`user_name` is required. Does **not** touch the telemetry log. |
| 7 | DELETE | `/api/telemetry` | the dashboard ("Clear telemetry" button) | Remove stored telemetry (token/credit usage) records for one session (`?session_id=...`), every session belonging to one user (`?user_name=...`), or every session reported from one machine (`?machine_name=...`). Exactly one of the three is required. `user_name`/`machine_name` are resolved to session id(s) via the heartbeat data already recorded through `/api/health`. Does **not** touch heartbeat/liveness data. |

All seven require an `X-API-Key: <secret>` header. `/healthz` (used for
Docker/Kubernetes health probes) and `/` and `/static/*` (the dashboard
itself) do not require it, since the dashboard's own JavaScript is what
attaches the header when it calls the APIs above.

Interactive, browsable API documentation (auto-generated by FastAPI) is
available at `/docs` once the app is running -- open it in a browser to
see every endpoint, its parameters, and try requests directly.

## Source-control context fields

Every telemetry record and heartbeat can optionally carry a small set of
source-control fields, populated by `telemetry-handler.js` /
`telemetry-watcher.js` from the repository (if any) present in the
working directory at the time of the event. These field names match
exactly what those scripts actually send. All are optional -- a session
may not be inside a repository at all -- and all pass through unchanged
if omitted (the existing `extra = "allow"` policy on the telemetry model
means older handler/watcher versions that don't send these fields yet
keep working exactly as before):

| Field           | Meaning |
|------------------|---------|
| `project_name`   | The project name as reported by the handler/watcher, e.g. `"APIM-Kong-DevOps"`. Usually the same value as `repo_name`, but reported separately in case they diverge (e.g. a monorepo subproject). |
| `repo_name`      | The repository name, e.g. `"APIM-Kong-DevOps"`. Used to group usage by repository regardless of remote host, protocol, or organization. |
| `organization`   | The organization/account that owns the remote repository, e.g. `"ericsson"`. Parsed from the remote URL. |
| `branch`         | The current branch checked out at the time of the event, e.g. `"main"` or `"master"`. |
| `scm_type`       | The source-control hosting platform, e.g. `"Azure DevOps"`, `"GitHub"`, or `"GitLab"`. Distinct from `vcs_type` (the underlying version-control tool). |
| `vcs_type`       | The version-control system in use, e.g. `"git"`. |
| `remote_url`     | The repository's remote URL exactly as reported by the handler/watcher, such as `https://ericsson@dev.azure.com/ericsson/APIM-Kong-DevOps/_git/APIM-Kong-DevOps`. |

Example `turn_tokens` payload (sent by `telemetry-handler.js` on every
Stop event) showing these fields in context:

```json
{
  "timestamp": "2026-08-24T13:42:53.638Z",
  "type": "turn_tokens",
  "session_id": "sess_...",
  "cwd": "/path/to/project",
  "model": "claude-sonnet-5",
  "project_name": "APIM-Kong-DevOps",
  "repo_name": "APIM-Kong-DevOps",
  "organization": "ericsson",
  "branch": "master",
  "scm_type": "Azure DevOps",
  "vcs_type": "git",
  "remote_url": "https://ericsson@dev.azure.com/ericsson/APIM-Kong-DevOps/_git/APIM-Kong-DevOps",
  "prompt_tokens_estimated": 0,
  "response_tokens_estimated": 0,
  "total_tokens_estimated": 0,
  "token_estimation_method": "tiktoken(cl100k_base) - approximation, not exact for this model"
}
```

These same fields are accepted on heartbeats (`POST /api/health`) too, so
a session can be attributed to an organization/repository/branch as soon
as it's known, even before any telemetry event has been recorded yet.

## Usage Analytics: `GET /api/telemetry/analytics`

This is the endpoint behind the dashboard's "Usage Analytics" section. A
single call returns everything needed to drive the Overview, Detailed
Records, and Charts tabs for one filter selection:

```json
{
  "total_matching_records": 42,
  "aggregate": [ { "group_key": "...", "organization": "...", "repo_name": "...", "project_name": "...", "branch": "...", "scm_type": "...", "vcs_type": "...", "user_name": "...", "session_id": "...", "turn_count": 5, "total_prompt_tokens": 1200, "total_response_tokens": 3400, "total_tokens": 4600, "total_credits_used": 2.35, "first_seen_at": "...", "last_seen_at": "..." } ],
  "daily_series": [ { "date": "2026-08-20", "turn_count": 3, "total_tokens": 4600, "total_credits_used": 2.35 } ],
  "records": [ /* individual TelemetryRecordOut entries, most recent first */ ],
  "filter_options": { "user_names": [...], "session_ids": [...], "organizations": [...], "repo_names": [...], "project_names": [...], "branches": [...], "scm_types": [...], "vcs_types": [...] }
}
```

Query parameters (all optional, combine with AND):

| Parameter            | Meaning |
|-----------------------|---------|
| `user_name`           | Only include records belonging to sessions reported by this user (resolved via heartbeat data, same cross-reference pattern used by the existing telemetry-clear-by-user feature). |
| `session_id`          | Only include records for this Kiro session id. |
| `organization`        | Only include records from this organization/account, e.g. `"ericsson"`. |
| `repo_name`           | Only include records from this repository name. |
| `project_name`        | Only include records from this project name. |
| `branch`              | Only include records recorded on this branch. |
| `scm_type`            | Only include records hosted on this SCM platform, e.g. `"Azure DevOps"`, `"GitHub"`. |
| `vcs_type`            | Only include records from this version-control system, e.g. `"git"`. |
| `start_date` / `end_date` | Only include records with an event timestamp within this (inclusive) ISO-8601 date/time range. |
| `group_by`            | Comma-separated dimensions to group `aggregate` by. Default: `organization,repo_name,branch,user_name,session_id`. Any subset of `user_name`, `session_id`, `organization`, `repo_name`, `project_name`, `branch`, `scm_type`, `vcs_type`, `remote_url` is valid, e.g. `group_by=repo_name` for one row per repository. |
| `record_limit`        | Maximum number of entries in `records` (1-5000, default 500). `aggregate` and `daily_series` always reflect every matching record regardless of this limit. |

Because telemetry records only carry a `session_id` (not
`user_name`/`machine_name` directly), the `user_name` filter is resolved
to session id(s) via heartbeat data the same way the existing
machine/user telemetry-clear feature already does. There is no secondary
Redis index on any of the source-control dimensions -- each request
scans the telemetry index once (capped at the most recent 20,000
records), which is the same "scan and filter in Python" approach the
service already uses elsewhere; acceptable for this proof-of-concept's
expected volume.

## Configuration: .env.development vs .env

This app loads configuration from a `.env`-style file automatically at
startup, using [`python-dotenv`](https://pypi.org/project/python-dotenv/)
(see `app/config.py`). Which file gets loaded depends on the
`ENVIRONMENT` variable:

| `ENVIRONMENT` value        | File loaded         | Typical use                          |
|-----------------------------|----------------------|----------------------------------------|
| `development` (or unset)    | `.env.development`  | Local development (`uvicorn --reload`) |
| `production`                 | `.env`               | Docker / Kubernetes / real deployments |

Real process environment variables (`export ...`, `docker run -e ...`,
Kubernetes `env:`/`envFrom:`) always take priority over whatever is in
these files -- the files only fill in values that aren't already set.
This means the same Docker image works unmodified everywhere: pass real
secrets as environment variables in Docker/Kubernetes, and they'll be
used as-is even if a `.env` file is also present (or absent) in the
image.

Both `.env.development` and `.env` already exist in this project as
starting points -- `.env.development` has convenience defaults for local
testing, `.env` has placeholder values you must replace before deploying
to production. **Neither file should be committed with real secrets**;
both are listed in `.gitignore`. `.env.example` remains as a documented,
safe-to-commit reference of every variable the app understands.

## 1. Running it locally (no Docker) -- for development/testing

You need Python 3.10+ installed.

```bash
cd /study/poc/kiro-trace

# Create an isolated Python environment for this project's dependencies
# (keeps them separate from anything else installed on your system).
python3 -m venv .venv
source .venv/bin/activate

# Install the exact package versions this project was tested with
# (includes python-dotenv, used to load .env.development / .env below).
pip install -r requirements.txt

# Edit .env.development with your local Redis details / API key if the
# defaults already in the file don't match your setup, then just run:
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

No `export` statements are required -- `app/config.py` automatically
loads `.env.development` (since `ENVIRONMENT` is unset, which defaults to
`development`). If you'd still rather use real environment variables
instead of/in addition to the file, they will always win over whatever
is in `.env.development`.

Then open **http://localhost:8000/** in a browser -- that's the
dashboard. Paste the same value you set for `API_KEY` (in
`.env.development`) into the "API Key" box at the top and click Save;
the dashboard will start showing data.

To stop the server, press `Ctrl+C` in the terminal it's running in.

## 2. Running it with plain Docker

Build the image once:

```bash
cd /study/poc/kiro-trace
docker build -t kiro-trace:latest .
```

Run it (this example assumes Redis is reachable from your host machine
at `localhost:6379`; `host.docker.internal` is the special hostname
Docker provides so a container can reach services running on your host
machine). This sets `ENVIRONMENT=production` so the app knows it would
load `.env` if one were present in the image -- but since `.env` is
git-ignored and therefore NOT copied into the image by the `Dockerfile`,
every setting must be passed explicitly via `-e` here, which is the
recommended approach for containers anyway:

```bash
docker run -d --name kiro-trace \
  --add-host=host.docker.internal:host-gateway \
  -p 8000:8000 \
  -e ENVIRONMENT=production \
  -e REDIS_HOST=host.docker.internal \
  -e REDIS_PORT=6379 \
  -e REDIS_USERNAME=default \
  -e REDIS_PASSWORD=redis123 \
  -e API_KEY=replace-with-a-real-secret \
  kiro-trace:latest
```

Check it started correctly:

```bash
docker logs kiro-trace
curl http://localhost:8000/healthz
```

Stop and remove it when you're done:

```bash
docker rm -f kiro-trace
```

## 3. Running it on Kubernetes

Below is a minimal, complete set of manifests. Adjust the namespace,
image name/registry, and `REDIS_HOST` to match your actual cluster
(the user's Redis instance runs in a namespace called `redis` -- if this
app runs in a *different* namespace, use the fully-qualified Service DNS
name `redis.<redis-namespace>.svc.cluster.local` instead of a short name).

Save this as `k8s-manifests.yaml` (or split into separate files if you
prefer):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: kiro-trace-secrets
  namespace: default
type: Opaque
stringData:
  REDIS_PASSWORD: "redis123"
  API_KEY: "replace-with-a-real-secret"
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: kiro-trace-config
  namespace: default
data:
  ENVIRONMENT: "production"
  REDIS_HOST: "redis.redis.svc.cluster.local"
  REDIS_PORT: "6379"
  REDIS_USERNAME: "default"
  TELEMETRY_TTL_SECONDS: "604800"
  APP_PORT: "8000"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kiro-trace
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      app: kiro-trace
  template:
    metadata:
      labels:
        app: kiro-trace
    spec:
      containers:
        - name: kiro-trace
          image: kiro-trace:latest   # push this image to a registry your cluster can pull from
          ports:
            - containerPort: 8000
          envFrom:
            - configMapRef:
                name: kiro-trace-config
            - secretRef:
                name: kiro-trace-secrets
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8000
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8000
            initialDelaySeconds: 10
            periodSeconds: 15
---
apiVersion: v1
kind: Service
metadata:
  name: kiro-trace
  namespace: default
spec:
  selector:
    app: kiro-trace
  ports:
    - port: 8000
      targetPort: 8000
  type: ClusterIP   # change to NodePort or LoadBalancer if you need it reachable from outside the cluster
```

Apply it:

```bash
kubectl apply -f k8s-manifests.yaml
kubectl get pods -l app=kiro-trace
kubectl logs -l app=kiro-trace
```

To reach the dashboard from your own machine without exposing it
publicly, use `kubectl port-forward`:

```bash
kubectl port-forward svc/kiro-trace 8000:8000
```

Then open http://localhost:8000/ as before.

**Security note:** the manifest above stores `API_KEY` and
`REDIS_PASSWORD` in a Kubernetes `Secret`, which is the standard
mechanism for this -- but plain `Secret` objects are only
base64-encoded, not encrypted, unless your cluster has encryption-at-rest
and/or a secrets manager (e.g. Sealed Secrets, External Secrets, Vault)
configured. Treat the values in `stringData` above as placeholders you
must replace, and manage the real secret according to your
organization's policy rather than committing it to version control.

## Connecting the Kiro CLI handler/watcher scripts to this server

By default, `telemetry-handler.js` and `telemetry-watcher.js` (in
`~/.kiro/handlers/`) only write to the local `~/.kiro/logs/telemetry.log`
file -- pushing to this web service is optional and additive. To enable
it, set these two environment variables in the shell that launches your
Kiro CLI session (e.g. in your `~/.bashrc` or `~/.profile`):

```bash
export KIRO_TRACE_API_URL=http://localhost:8000      # or your deployed URL
export KIRO_TRACE_API_KEY=replace-with-a-real-secret  # must match this server's API_KEY
```

Once set, every hook invocation and every watcher-detected credit event
will also be pushed to this server's `/api/telemetry` endpoint, and the
watcher will send a heartbeat to `/api/health` every 5 minutes (this
interval is configurable via `KIRO_TRACE_HEARTBEAT_INTERVAL_MS`, in
milliseconds).

If `KIRO_TRACE_API_URL` is left unset, the handler/watcher scripts behave
exactly as before -- local file logging only, no network calls at all.

**Note on source-control fields:** `app/models.py` in this project now
accepts `project_name`, `repo_name`, `organization`, `branch`,
`scm_type`, `vcs_type`, and `remote_url` on both `/api/telemetry` and
`/api/health` payloads (see "Source-control context fields" above,
matching exactly what `telemetry-handler.js` / `telemetry-watcher.js`
actually send), and the dashboard's "Usage Analytics" section filters
and charts on them. These fields are optional and backward compatible --
the server accepts payloads with or without them.

## Dashboard layout

Opening `http://<host>:8000/` shows:

- **Usage Analytics** (the primary view) -- a filter bar to narrow usage
  by user, session, organization, repository, project name, branch, SCM
  type, VCS type, and a from/to date range, with an "ⓘ" tooltip on every
  field explaining exactly what it means. A summary strip above the tabs
  shows the computed totals (matching events, turns, tokens, credits
  used, and number of groups) for whatever is currently filtered. Three
  tabs present the same filtered selection three ways:
  - **Overview** -- computed aggregates, grouped by organization,
    repository, branch, user, and session (configurable via the "Group
    by" dropdown), sorted by credits used so the biggest consumers are
    always at the top.
  - **Detailed Records** -- individual telemetry events, most recent
    first, including their source-control context, for anyone who needs
    record-level detail rather than totals.
  - **Charts** -- token usage and credit usage trends by day over the
    selected date range, plus a bar chart of credits used by
    repository, so usage/cost patterns are visible at a glance. These
    are drawn as inline SVG with no external charting library, so the
    dashboard keeps working fully offline.
- **Fleet Health by Machine & Session** -- a management view of
  liveness/heartbeat status, grouped by **machine &rarr; user &rarr;
  session**, with each session row showing a turn count, token/credit
  totals, last-active time, and two status icons ("H" for handler, "W"
  for watcher) that are green when that component's last heartbeat is
  recent and red when it's stale. Click an icon to see that component's
  full heartbeat detail, including its source-control context if known.
  - A "Clear heartbeat data" button per user and per session, which
    removes stored `/api/health` heartbeat entries for that scope after
    a confirmation prompt. This only clears heartbeat/liveness data -- it
    never deletes telemetry log entries (token/credit usage history is
    left untouched).
  - A "Clear telemetry" button per machine, per user, and per session,
    which permanently removes stored `/api/telemetry` usage records
    (token/credit history) for that scope after a confirmation prompt.
    This only clears telemetry data -- it never touches heartbeat/liveness
    data. The per-machine and per-user buttons resolve to the matching
    session id(s) via the heartbeat data already recorded through
    `/api/health`, so a machine/user with no recorded heartbeat has
    nothing to clear this way (clear by session id instead).
- A fleet-level summary strip (machines, users, sessions, active
  components, total credits used, total tokens) sits above both
  sections for an at-a-glance management view of the whole fleet,
  independent of the Usage Analytics filters.

## Capturing prompt/response text (optional, off by default)

Two independent settings in `~/.kiro/settings/cli.json` control whether
the raw prompt text and/or raw response text are included in telemetry
records (both locally and, if configured, pushed to this server):

```json
{
  "telemetry.captureRequestPayload": false,
  "telemetry.captureResponsePayload": false
}
```

Each is checked independently -- you can enable one without the other.
Both default to `false` (disabled) if not present at all. Turning either
one on means the corresponding text (what you typed, and/or what Kiro
responded) will be stored in the local log file and, if remote push is
enabled, transmitted to and stored in this server's Redis instance.
Treat that data as sensitive if your prompts/responses could contain
confidential information.

## How data expires

Telemetry records are stored in Redis with an automatic expiry
(`TELEMETRY_TTL_SECONDS`, 7 days by default) -- old records disappear on
their own, you don't need to run any cleanup job. To remove telemetry
data sooner than that, use the dashboard's "Clear telemetry" button (by
machine, user, or session), or call `DELETE /api/telemetry` directly.
Health heartbeats have no expiry (only the single latest heartbeat per
session+component is kept, so that data can't grow unbounded over time
either) -- use the dashboard's "Clear heartbeats" button, or `DELETE
/api/health` directly, to remove heartbeat entries for a session/user
once they're no longer needed. The two clear actions are independent:
clearing telemetry never touches heartbeat data and vice versa.

## Troubleshooting

- **"Server misconfiguration: API_KEY environment variable is not set"**
  -- you started the app without setting `API_KEY`. Set it and restart.
- **Dashboard shows "not connected"** -- the API key typed into the
  dashboard doesn't match the server's configured `API_KEY`, or the
  server isn't reachable. Check the browser's developer console (F12)
  for the specific error.
- **Handler/watcher scripts aren't showing up here at all** -- confirm
  `KIRO_TRACE_API_URL` and `KIRO_TRACE_API_KEY` are set in the same shell
  environment the Kiro CLI itself was launched from (env vars set in one
  terminal don't apply to a Kiro CLI session already running in another
  terminal -- you'll need to restart that terminal/session after setting
  them).
